## Expected vs Actual Outcome

The new docs and tutorials are executable, and the documented commands mostly behave as promised. The main issue is not that commands fail, but that the core recovery API currently reports blind recovery based on the unsnapped model output. That is a correctness problem in the implementation, not in the docs.

## Issues Found

- High: [`src/eval/Recovery.jl`](/Users/terasaki/tmp/eml/src/eval/Recovery.jl:13) builds `recovered = snap_model(...)`, but the verdict at [line 17](/Users/terasaki/tmp/eml/src/eval/Recovery.jl:17) and [lines 19-23](/Users/terasaki/tmp/eml/src/eval/Recovery.jl:19) is computed from `Lux.apply(layer, xs, training.params, training.state)`, i.e. the continuous pre-snap model. This means `recovery.success` does not actually validate the snapped tree described by the docs.
- Medium: [`scripts/export_recovered_formulas.jl`](/Users/terasaki/tmp/eml/scripts/export_recovered_formulas.jl:6) still prints only `target`, `seed`, and `formula`, so once multiple configs coexist in `results/raw/`, the formula listing remains ambiguous.

## Suggestions

- Evaluate the snapped representation itself inside `run_experiment`, or at minimum reconstruct snapped parameters and score those predictions when computing `RecoveryVerdict`.
- Include `config_name` and ideally `depth` in `export_recovered_formulas.jl` output so tutorial users can interpret mixed result sets correctly.
